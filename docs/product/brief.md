# 하루의 이야기 제품 개요와 주요 결정

2026-11-26 제품 논의를 바탕으로 서비스 컨셉, 결정 사항, 데스크톱 화면 기준과 내부 MVP의 검토 과제를 정리한다. 최신 사용자 결정과 실제 저장소 상태를 각 주제의 기준으로 삼는다. 결정 상태(확정·잠정·제안·미결정·폐기)와 구현·검증 상태는 별도로 본다.

## 서비스 컨셉과 제품 방향

‘하루의 이야기’는 사용자가 일기와 사진으로 하루를 기록하고 다시 읽으며, 선택한 기록을 AI로 글·그림 이야기로 재창작하는 개인 기록 앱이다. **일기 작성과 다시 읽기가 중심이고 AI 재창작은 그 기록에서 자연스럽게 이어지는 확장 기능이다.**

확정된 제품 방향은 다음과 같다.

1. 하루에 여러 기록을 작성할 수 있고 날짜별로 모아 보여준다.
2. 별도 제목 입력 없이 본문 첫 줄을 목록에 활용한다.
3. 사진 첨부와 사용자 정의 분류를 지원한다.
4. 원본 일기는 비공개이며 이야기 생성 뒤에도 보존한다. 사용자가 직접 일기를 수정할 수 있고 AI 생성은 원본에 손대지 않는다.
5. 이야기 생성 목적은 개인 보관과 다른 사람에게 보여줄 용도를 모두 지원한다.
6. 생성 결과도 기본 비공개다. ‘보여줄 용도’를 골라도 자동 공개하지 않는다.
7. 공유는 복사하거나 파일을 저장해 사용자가 직접 게시하는 방식이다. MVP에서 공유 자체에 별도 과금하지 않는다. 생성·재생성 등의 전체 무료 정책은 미결정이다.
8. 기본 스타일은 AI가 판단하되, 사용자가 명시적으로 선택한 저장 스타일을 우선한다.
9. 생성 목적·재생성·수정 요청·다운로드 등 사용자 행동을 분석할 필요가 있다. 수집 동의·도구·기간은 미결정이다.
10. 첫 MVP는 내부 기능 검증용 데스크톱 앱이며 관리자 대시보드를 포함한다.
11. 향후 iOS·Android 확장을 고려하고 하나의 저장소에서 관리한다. 모바일 출시 시점·코드 공유 범위·기기 간 동기화는 미결정이다.

‘이야기로 만들기’는 **잠정 기능명**이다. 출력 형태의 사용자용 이름과 스타일 선택 UX는 검증 대상이다. 첫 목표 고객의 연령·성별·직업, 인력·예산·출시일은 미결정이다.

README에 나오는 클라이언트의 `src/domain`, `src/application`, `src/adapters/tauri`와 백엔드의 `haru_backend/domain`, `haru_backend/application`, `services/backend/migrations`는 기능 추가 시 사용할 배치 경로다. 이 문서를 정리할 때 확인한 워킹 트리에는 기본 앱·서버·관리자 코드와 상태 확인 API가 있었고, 위 배치 경로는 아직 없었다. 제품 기능의 구현과 테스트·빌드 성공 여부는 별도 검증으로 기록한다.

## 데스크톱 디자인 기준

기준 시안은 ‘하루의 이야기 — 데스크탑 전체 주요 화면 시안 · v2’다. 시안 파일은 추후 `docs/` 하위에 첨부하고, 파일을 추가할 때 이 문서에서 링크한다. 첨부 전까지는 아래에 정리한 기존 논의의 UI 기준을 참고한다. 이미지와 검토 규칙이 다르면 검토 규칙을 적용하며, 최신 사용자 결정이 우선한다.

### 시각적 방향 — 등록된 UI 기준

- 기본 UI는 ‘하루의 흐름’ 시안을 바탕으로 하되 사용자 메뉴명은 **홈**이다.
- ‘시간의 정원’의 달력 기능을 추가한다.
- ‘인피니트 스페이셜 캔버스’는 자동 배치된 기록을 읽는 **펼쳐보기**다.
- 코럴·피치·화이트·세이지 계열의 일관된 색감을 사용한다.
- 펼쳐보기에는 펠트 도트 배경·메모·종이클립 사진 같은 기록물의 시각적 모티프가 있다.
- 기록 본문과 사진을 읽기 편하게 구성하고 화면 간 글꼴·여백·필터·진행 표시를 공통화한다.
- 세부 색상 코드와 컴포넌트 수치는 사용성 검증 후 확정한다.

다음 수치는 v2 검토 문서의 **구현 기준안**이며 사용성 검증 후 조정한다.

| 항목 | 기준안 |
| --- | --- |
| 기준 콘텐츠 영역 | 1440×900 논리 픽셀, OS 제목 표시줄 제외 |
| 최소 검토 영역 | 1024×700, 고정 창 크기 강제 아님 |

앱의 논리 크기는 위 콘텐츠 영역을 기준으로 삼는다. 글꼴 배포 조건, OS 렌더링, 한글 입력, 키보드 탐색과 접근성은 검증 대상이다.

### 명시적인 UI 동작 규칙

1. 내 기록과 만든 이야기는 독립된 탐색 범위이며 각 범위에서 홈·달력·펼쳐보기를 제공한다. 같은 데이터의 보기 방식이지 별도 원본 복제가 아니다.
2. 내 기록 달력은 기록 대상일, 만든 이야기 달력은 생성일을 기준으로 하며 날짜 의미를 표시한다.
3. 기본 필터는 검색·분류, 상세 필터는 날짜 범위·사진/그림 포함 여부다. 만든 이야기에는 출력 형태도 제공한다.
4. 같은 자료 범위의 보기 전환에서는 조건을 유지하고, 내 기록과 만든 이야기의 조건은 별도로 기억한다. 조건 칩·초기화·결과 없음에서 조건 해제를 제공한다.
5. 이야기 분류 검색은 원본 기록의 분류를 활용하고 결과를 중복 표시하지 않는다. 원본 없는 경우 미분류로 다룬다. 분류 편집은 원본 기록에서 한다.
6. 펼쳐보기는 열람 전용이다. 편집·올가미·카드 이동·연결·합성을 제공하지 않는다. 카드 선택은 읽기 초점이며 생성 재료 선택이 아니다.
7. 홈의 빠른 기록과 전체 작성의 넓게 쓰기는 같은 초안 ID·본문·사진·날짜·분류를 유지한다. 초안 자동 저장과 기록 완료를 구분하고 빈 초안을 기록으로 만들지 않는다. 기존 일기 수정이 새 일기를 중복 생성하지 않는다.
8. 생성 단계는 이야기 설정 → 전송 확인 → 만드는 중 → 결과 확인으로 통일한다. 미래 단계는 이동 버튼이 아니다. 이전 단계로 돌아가도 선택을 유지하고 생성 중에는 설정 변경을 잠근다.
9. 재생성은 이전 결과를 유지한 새 요청으로 전송 확인을 거친다. 취소는 상태별 의미·비용 정책을 먼저 결정한다.
10. 설정·개인정보·백업·복원에는 기록 보기 전환 탭을 넣지 않는다. 보관 관련 명칭은 기록 보관으로 통일하고 설정 → 기록 보관 → 암호화 백업 / 백업 복원으로 연결한다. 암호화·키·복구 정책은 미결정이다.

## MVP 상세 범위와 설계 후보

첫 내부 MVP의 데스크톱 검증과 관리자 대시보드 포함은 확정이다. 아래 항목은 상세 범위 **제안**이며, 항목별 구현 깊이와 포함 여부는 검토 대상이다.

- 초기 안내, 일기 작성·수정·조회·본문 검색, 사진과 분류, 날짜별 모음, 홈·달력·펼쳐보기와 공통 필터.
- 기록 선택, 생성 목적·출력·스타일 설정, 전송 확인, AI 생성 접수·진행·실패 표시와 재접속.
- 결과 열람·보관·원본 연결, 직접 편집·AI 수정 요청·재생성·버전 관리, 복사·파일 저장.
- 설정·저장 스타일·기록 보관·수동 백업·복원, 관리자 운영 지표와 허용된 행동 분석.

원본은 로컬에 두고 생성에 필요한 선택 기록의 텍스트와 사진만 서버에 보내는 방식이 후보이다. 로컬 DB, 사진·키 보관, 복구 방법과 함께 검토한다. 장시간 생성은 접수와 실행을 분리하는 방안을 검토한다. 서버 DB 기반 처리와 별도 큐를 내구성·운영 복잡도·비용 기준으로 비교한다. 큐·클라우드·AI 제공자 선정, 전체 일기 서버 CRUD와 동기화는 별도 결정이 필요하다.

작업 설계에는 생성 시점의 입력 고정과 원본 연결, 작업 상태, 멱등성, 제한된 재시도, 앱·워커 재시작 복구, 결과 버전과 보관·정리 정책을 포함해 검토한다. 호출·과금 중복 방지와 복구 범위는 제공자 계약에 맞춰 결정한다. 사용자 흐름에서는 서버 생성 완료, 앱 내 저장 완료, 외부 파일 저장 완료를 구분한다. 연결이 끊기면 상태를 다시 조회할 수 있어야 하며, 저장·다운로드 재시도와 새 생성 요청의 비용은 각각 다룬다.

관리자 화면의 최소 후보는 작업 건수·상태·대기/실행시간·오류·추정 비용·허용된 행동 집계다. 상세 권한과 원문 접근 및 작업 재실행 범위는 미결정이다. 분석은 원문·사진·자유 입력·수정 요청 본문 없이 수집하는 최소 이벤트를 우선 검토한다. 사전 동의, 보관, 철회, 관리자 접근을 결정하고, 복사·저장 이벤트는 복사·저장 행동까지만 집계한다. 개인 기록 자료는 비공개로 취급하며 실제 원문·사진·비밀값은 외부 게시물·예제·로그에 포함하지 않는다.

모바일 배포, 기기 간 동기화, 공동 편집, SNS 자동 게시, 공개 피드, 출판 주문, 자동 클라우드 백업은 초기 MVP의 제외 후보다.

## 후속 개발 계획의 검토 기준

당시 검토한 단계 후보는 M0 기준·미결정 정리 → M1 기존 기본 구성 실행 검증 → M2 로컬 일기 작성·조회 → M3 사진·분류·검색·달력·펼쳐보기 → M4 AI 생성 작업 → M5 결과 관리 → M6 백업·운영 검증이다. 관리자·분석·개인정보 요구는 관련 기능 단계에 함께 반영하고, 저장 형식·키·복구 경계는 저장 구현 전에 검토한다.

- **범위와 산출물** — 기능별 포함 여부와 구현 깊이를 정하고, 작업 ID·사용자 결과·대상 경로·담당 역할·선행 작업·결정 시한·산출물·완료 증거를 연결한다. 저장·AI 작업·전송·백업의 대안을 비교하며, GraphQL과 파일 업로드의 책임, 원본·입력 스냅샷·결과 버전의 수명주기를 포함한다.
- **공수와 비용** — 인력·숙련도·실작업 시간·대상 OS·코드 재사용·AI 도구 활용·품질 깊이를 가정으로 명시하고, 낙관·기준·보수 공수와 달력 기간을 구분한다. 시안 대조·한글 입력·복구·통합·검증·내부 배포 준비, 병렬 작업·임계 경로·대기 시간과 가용시간의 영향을 반영한다. AI·인프라 비용은 확인한 단가와 모델·생성 건수·재시도율·저장량으로 추정한다. 내부 MVP, 상용 출시, 모바일 확장 공수와 추정 갱신 시점은 각각 기록한다.
- **완료 증거** — 같은 날짜의 복수 기록, 동일 초안 전환, 수정 중복 방지, 원본 보존, 저장 스타일 우선, 보기 범위·필터 유지, 선택 자료 전송, 사용자·관리자 권한, 중복 생성·비용, 중단 후 복구, 결과·파일 저장 실패, 백업 복원을 검증한다. 합성 자료를 사용하고 모의 AI 계약 검사와 실제 모델 품질 검증을 각각 기록한다.
- **남은 결정** — 영향과 대안, 필요한 결정 시점, 결정 전 진행 가능한 작업을 기록한다. 계획용 가정과 구현 전에 필요한 승인을 각각 명시하고, 첫 개발 작업의 범위와 완료 조건을 정한다.
